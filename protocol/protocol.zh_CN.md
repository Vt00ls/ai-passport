# 仪表盘状态协议

主机通过 BLE 推送给 AI Passport 的紧凑状态串的唯一权威定义。主机侧参考实现：
`../host/protocol.py`。

## 目的

dev-forge 主机周期性地采集节点健康状态与 agent 活动，编码为一条紧凑的 ASCII
状态串，并通过 BLE 写入工牌。工牌解码后渲染三个页面：主机健康、agent 状态、
网络。工牌还会得出“最后心跳距今时间”，用来满足节点监控需求：收到一条状态就
开始计时，此后收不到就持续计时，于是冻结或重启的主机会在屏幕上显现出来。

工牌本身没有墙上时钟（无 RTC 电池，且联网不在范围内），因此必须用自身的单调
时钟以“距最后一次成功收到状态的时长”来衡量这个时间，绝不能用“工牌时钟 − `t`”
去算。`t` 字段仍然保留，它是主机自己的时间戳：用于发现主机时钟跳变、支撑主机
侧诊断，也是未来某个已同步时钟的工牌可以直接使用的值。

## 线上格式

```text
v=1;t=1782530000;h=dev-forge;up=86400;ld=0.42;cpu=7;mem=38;dsk=33;tmp=51;net=eno1,up,10.2.65.61;ag=2;as=5
```

规则：

- 纯 ASCII 的 UTF-8 文本；末尾无 `;`。
- 有序的 `key=value` 对，以 `;` 连接。键固定为小写，按下表所列字段顺序发送。
- `v` 与 `t` 为必填。其余字段均为可选，生产端无法测得时必须省略（不得发空值）；
  工牌对缺失字段显示“无数据”。
- 编码后总长度不得超过 **200 字节**，以便在 MTU 协商后由一次 BLE ATT 写入携带。
  工牌必须协商至少 200 字节有效载荷的 ATT MTU（ESP32-C3 协议栈支持到 517 的
  MTU 交换）。
- 值字符集仅限 `[A-Za-z0-9._/-]`。`net` 额外使用 `,` 作为内部分隔符。任何值都
  不得包含 `;`、`=`、空格或换行。生产端需净化：丢弃非法字符；结果为空时填 `-`。

## 字段

| 键 | 类型 | 含义 | 示例 |
| --- | --- | --- | --- |
| `v` | int | 协议版本，当前为 `1`。必须是第一个字段。 | `v=1` |
| `t` | int | 采集时主机墙上时钟的 Unix 秒数，即心跳。 | `t=1782530000` |
| `h` | str | 主机名（已净化）。 | `h=dev-forge` |
| `nc` | int | 在线逻辑 CPU 核数，1–1024。没有它 `ld` 无法判断高低。 | `nc=4` |
| `up` | int | 运行时长，秒。 | `up=86400` |
| `ld` | str | 1 分钟负载均值，固定两位小数。要结合 `nc` 判断。 | `ld=0.42` |
| `cpu` | int | CPU 忙百分比，0–100。 | `cpu=7` |
| `mem` | int | 内存已用百分比，0–100。 | `mem=38` |
| `dsk` | int | 根文件系统已用百分比，0–100。 | `dsk=33` |
| `tmp` | int | CPU 封装温度，°C，范围 −40 到 125。 | `tmp=51` |
| `net` | str | `接口,状态,IP`；`状态` 为 `up` 或 `down`，`IP` 为 IPv4 或 `-`。 | `net=eno1,up,10.2.65.61` |
| `ag` | int | 活跃 agent 会话数：最近 300 秒内有活动的会话数。 | `ag=2` |
| `as` | int | 距最近一次 agent 活动的秒数；从未活动则为 `-1`。 | `as=5` |

字段到页面的映射：

- 主机健康页：`up`、`ld`、`cpu`、`mem`、`dsk`、`tmp`。
- 网络页：`net`。
- agent 状态页：`ag`、`as`。
- 心跳横幅（所有页面）：距今 = 工牌单调时钟 − 最后一次成功收到状态时的单调时刻。
  不使用 `t` 与工牌时钟比较。

## 推送节奏与链路分级

连接正常时生产端每 **5 秒** 发布一条状态。工牌按下表的“距今”值对链路分级：

| 链路状态 | 距今 | 工牌呈现 |
| --- | --- | --- |
| none | 开机后或最后一次断开后从未收到过状态 | 所有字段显示“无数据” |
| live | 0–15 秒 | 正常数值，心跳点绿色 |
| stale | 16–120 秒 | 数值变暗，心跳点琥珀色；仍显示距今时长 |
| lost | > 120 秒 | 数值替换为“无数据”，心跳点红色；仍显示距今时长 |

BLE 断开会立即清空测得的数值，但保留最后心跳时间戳，所以主机重启期间“距今”会
继续增长。

## 解码约定

符合规范的解码器必须：

1. 按 `;` 拆分；每一段必须恰好包含一个 `=`。
2. 拒绝未知键与重复键；只接受上表中的键。
   因为这条规则，新增字段必须让解码端与生产端在同一个 commit 里改完。
   不存在“解码器忽略未知键”的兼容退回：拒绝才能让版本不一致暴露出来，而不是静默。
3. 按上表逐键校验值的字符集与类型。
4. 要求存在 `v` 与 `t`；其余字段缺失视为“无数据”，而非错误。
5. 绝不把缺失的可选字段当作致命解析错误。

两份参考实现都会用同一份共享用例文件
[`fixtures/status_cases.txt`](fixtures/status_cases.txt) 校验，使主机编码端与固件
解码端不会在无人察觉的情况下产生偏差。

## 版本管理

- `v=1` 为冻结基线。因为解码端拒绝未知键，新增键属于**两端协同变更**，必须在同一个
  commit 内同时交付，并不向后兼容。
- 破坏性变更（键重命名/删除、线上分帧变化、新增必填键）必须递增 `v`。工牌拒绝 `v`
  大于其实现版本的载荷。
